# Implementation Plan: Retail Replenishment Decision Agent

Date: 2026-06-09
Status: Accepted
Feature spec: `docs/features/01 - retail-replenishment-agent.md`

## Objective

Implement the retail replenishment demo as an autonomous workflow agent, not a
chat assistant. The finished binary supports `seed`, `simulate`, `decide`, and
`run-cycle`; stores durable retail state in SQLite through Diesel migrations;
uses clean domain/application/infrastructure/interface boundaries; and lets a
Rig-backed decision agent propose restock orders that application code validates
and persists.

## Architecture Decisions

- Replace the current support/RAG tutorial surface with the retail workflow.
  Remove the old REPL, order-status demo tools, vector-store setup, and support
  document indexing from the runtime path.
- Keep `src/main.rs` as a minimal async entrypoint that calls `rigagent::run()`.
- Organize behavior by layer:
  - `src/domain/retail/`: value objects, entities, aggregates, domain services,
    and `DomainError`.
  - `src/application/retail/`: commands, queries, ports, use cases, read models,
    and `ApplicationError`.
  - `src/infrastructure/`: Diesel persistence, migrations bootstrap, scenario
    loading, clocks/IDs, and the Rig-backed decision-agent adapter.
  - `src/interfaces/`: Clap CLI parsing, command dispatch, and interface errors.
- Use `chrono::NaiveDate` only behind the domain `SimulationDate` value object.
  Do not expose raw `chrono` types from application commands or domain entities.
- Avoid float arithmetic entirely. Store demand rates and demand backlog as
  fixed-point milli-units, for example `DemandRatePerDay(1250)` for 1.250
  units/day.
- Use checked or saturating arithmetic for all inventory, capacity, demand, and
  profit calculations. Avoid `as` casts; use `TryFrom`, `From`, and typed
  constructors.
- Use `thiserror` for all crate-owned error enums. Keep `anyhow` only at the
  binary edge for top-level process reporting if needed.

## Phase 2: Domain Model

Create `src/domain/retail/` with small focused modules and re-exports from
`mod.rs`.

Value objects:

- `Sku`: non-empty, trimmed, canonical uppercase SKU string.
- `Brand`: non-empty display name.
- `ApparelKind`: enum for closed item kinds, for example `Shirt`, `Pants`,
  `Jacket`, `Dress`, `Shoes`, `Accessory`.
- `SizeLabel`: enum or validated newtype supporting common apparel sizes.
- `MoneyCents`: non-negative cents with checked addition, subtraction, and
  multiplication by quantities.
- `SpaceUnits`: non-negative capacity units with checked addition and
  multiplication by quantities.
- `StockQuantity`: non-negative quantity with checked add/subtract.
- `DemandRatePerDay`: fixed-point milli-units/day parsed from a decimal string
  or integer milli-units.
- `DemandBacklog`: fixed-point milli-units carried between simulated days.
- `LeadTimeDays`: non-zero bounded day count.
- `DecisionHorizonDays`: non-zero bounded day count.
- `SimulationDate`: checked wrapper around `chrono::NaiveDate` with date
  addition through checked chrono APIs.
- IDs: `SalesOrderId`, `RestockOrderId`, and `DecisionRunId`, backed by UUIDs
  or validated strings generated by the infrastructure `IdGenerator`.

Entities and behavior:

- `Product`
  - Owns SKU, type, brand, size, unit cost, unit price, space units, demand
    rate, lead time, order quantity bounds, and active state.
  - Exposes `unit_margin()`, `restock_eta(current_date)`, and
    `bounded_order_quantity(requested_quantity)`.
- `InventoryPosition`
  - Owns SKU, on-hand units, and demand backlog.
  - Exposes `receive_restock(quantity)`, `fulfill_demand(requested_units)`, and
    `occupied_space(product)`.
- `RestockOrder`
  - Owns SKU, quantity, order date, ETA, status, decision run ID, and rationale.
  - Status enum: `Open`, `Received`, `Cancelled`.
  - Exposes transition methods such as `receive(on_date)` and rejects invalid
    transitions.
- `SalesOrder`
  - Records requested units, fulfilled units, revenue, cost, and lost units for
    a simulated sale event.
- `DecisionRun`
  - Tracks decision date, horizon, status, summary, and created restock count.
  - Status enum: `Started`, `Completed`, `Failed`.

Domain services:

- `DemandSimulator`
  - Converts `DemandRatePerDay + DemandBacklog` into requested whole units and
    remaining backlog without floats.
- `RestockOptionScorer`
  - Scores candidate restocks using expected incremental units available after
    ETA, unit margin, occupied space, open inbound stock, and capacity.
  - Returns ranked `RestockOption` domain/application DTOs without model or
    persistence types.

Domain tests:

- `rejects_empty_sku`
- `parses_decimal_demand_rate_without_float_arithmetic`
- `carries_fractional_demand_backlog`
- `rejects_restock_quantity_outside_product_bounds`
- `receives_open_restock_order`
- `rejects_receiving_cancelled_restock_order`
- `prevents_inventory_from_exceeding_capacity`
- `computes_profit_with_checked_cents_arithmetic`

## Phase 3: Application Layer

Create `src/application/retail/` with commands, queries, ports, use cases, read
models, and fakes for tests.

Commands and queries:

- `SeedRetailScenario`
  - Fields: scenario path, reset flag.
  - Behavior: fail if durable state exists and `reset` is false.
- `AdvanceSimulation`
  - Fields: days to advance.
  - Behavior: for each day, receive due restocks, simulate demand, record sales,
    update inventory, and advance the shop date.
- `RunRestockDecision`
  - Fields: horizon days and max restock orders.
  - Behavior: create a decision run, gather snapshot/options, call
    `ReplenishmentDecisionAgent`, validate proposals, persist accepted restock
    orders, and complete/fail the decision run.
- `RunWorkflowCycle`
  - Fields: total days, decision interval days, horizon days, max restock
    orders.
  - Behavior: run an initial decision on day 0, then simulate one day at a time;
    after every `decision_interval_days`, run another decision until total days
    are complete.
- `GetRetailSnapshot`
  - Returns current date, capacity usage, products, inventory, open restocks,
    recent sales, and profit summary.

Ports:

- `RetailStore`
  - `load_snapshot`
  - `seed_scenario`
  - `receive_due_restocks`
  - `record_sales_day`
  - `place_restock_orders`
  - `open_restock_orders`
  - `profit_summary`
  - `advance_shop_date`
- `DecisionRunStore`
  - `start_decision_run`
  - `complete_decision_run`
  - `fail_decision_run`
  - `decision_run`
- `ReplenishmentDecisionAgent`
  - Accepts a typed decision request containing snapshot, ranked restock
    options, open orders, horizon, and max orders.
  - Returns proposed restock orders and a rationale summary.
  - Use return-position `impl Future` or a concrete generic adapter; avoid
    adding `async-trait` unless object-safe dynamic dispatch becomes necessary.
- `Clock`
  - Supplies dates only where real time is needed. Simulation date should come
    from `shop_state`, not the system clock.
- `IdGenerator`
  - Generates typed IDs for sales orders, restock orders, and decision runs.

Application rules:

- Use cases own transaction boundaries and call ports through constructor
  injection.
- Application code validates every decision-agent proposal before persistence.
- Reject proposals for unknown SKUs, inactive products, non-positive
  quantities, quantities outside min/max bounds, duplicate open restock orders
  when policy disallows them, or orders that would exceed projected capacity.
- Persist rejected proposals only if a future audit table is added; v1 should
  return rejected proposal details in the decision result.
- Do not expose Diesel, Rig, Clap, serde YAML DTOs, or provider payloads in
  application APIs.

Application tests:

- Use hand-written in-memory fakes for every port.
- Fakes store domain types and enforce the same uniqueness and transition
  expectations needed by use-case tests.
- Add explicit failure injection for not found, duplicate order, transaction
  failure, invalid persisted data, and provider/agent failure.
- Cover:
  - `seed_requires_reset_when_state_exists`
  - `advance_simulation_receives_due_restock_before_sales`
  - `advance_simulation_records_lost_sales`
  - `run_decision_persists_accepted_agent_proposals`
  - `run_decision_rejects_capacity_overflow_proposal`
  - `run_decision_marks_run_failed_on_agent_error`
  - `run_cycle_decides_on_day_zero_and_each_interval`

## Phase 4: Diesel Persistence And Migrations

Create Diesel migrations under:

- `migrations/2026-06-09-000001_create_retail_state/up.sql`
- `migrations/2026-06-09-000001_create_retail_state/down.sql`

Migration requirements:

- `shop_state`
  - Single-row table with `id INTEGER PRIMARY KEY CHECK (id = 1)`.
  - `current_date TEXT NOT NULL`.
  - `capacity_space_units INTEGER NOT NULL CHECK (capacity_space_units >= 0)`.
- `products`
  - `sku TEXT PRIMARY KEY`.
  - Text fields for item type, brand, and size.
  - Integer fields for cents, space units, demand milli-units, lead time, and
    quantity bounds.
  - Checks for non-negative money/space/rate/quantity and positive lead time.
  - Check `max_order_quantity >= min_order_quantity`.
  - `active BOOLEAN NOT NULL`.
- `inventory`
  - `sku TEXT PRIMARY KEY REFERENCES products(sku)`.
  - `on_hand INTEGER NOT NULL CHECK (on_hand >= 0)`.
  - `demand_backlog_milli_units INTEGER NOT NULL CHECK (...)`.
- `sales_orders`
  - `id TEXT PRIMARY KEY`.
  - Sale date, SKU FK, requested/fulfilled/lost units, revenue, and cost.
  - Checks that quantities and money are non-negative.
- `restock_orders`
  - `id TEXT PRIMARY KEY`.
  - SKU FK, quantity, order date, ETA, status, decision run ID, and rationale.
  - Status check limited to `open`, `received`, `cancelled`.
  - Index open orders by SKU and ETA.
- `decision_runs`
  - `id TEXT PRIMARY KEY`.
  - Decision date, horizon, status, summary, and created restock count.
  - Status check limited to `started`, `completed`, `failed`.

Infrastructure implementation:

- Add `src/infrastructure/persistence/`.
- Keep Diesel generated schema and row structs private inside infrastructure.
- Implement `DieselRetailStore` and `DieselDecisionRunStore`.
- Use an r2d2-backed SQLite connection pool so Rig tools and workflow adapters
  can be `Send + Sync` without sharing a raw SQLite connection.
- Run embedded migrations during startup for commands that access retail state.
- Map Diesel row structs into domain types with `TryFrom`, preserving
  conversion failures as `InfrastructureError::InvalidPersistedData`.
- Wrap multi-write operations in Diesel transactions.
- Map Diesel errors into structured `InfrastructureError` variants:
  `NotFound`, `UniqueViolation`, `ForeignKeyViolation`, `MigrationFailed`,
  `PoolFailed`, `SerializationFailed`, and `InvalidPersistedData`.

Persistence tests:

- Use an isolated temporary SQLite database per test.
- Run real embedded migrations before each adapter test.
- Cover scenario seeding, due restock receipt, sales-day writes, transaction
  rollback on failure, unique/foreign-key violation mapping, and invalid row
  conversion.

## Phase 5: Scenario YAML And Seed Data

Create `data/retail_scenario.yaml`.

YAML shape:

```yaml
shop:
  start_date: "2026-06-09"
  capacity_space_units: 240

products:
  - sku: "TSH-ACME-M-BLK"
    item_type: "shirt"
    brand: "Acme"
    size: "M"
    unit_cost_cents: 1200
    unit_price_cents: 2999
    space_units: 2
    initial_on_hand: 18
    daily_demand_rate: "2.750"
    restock_lead_time_days: 4
    min_order_quantity: 6
    max_order_quantity: 36
```

Scenario loader:

- Add `src/infrastructure/scenario/`.
- Deserialize into infrastructure DTOs only.
- Convert DTOs into domain types through checked constructors.
- Parse `daily_demand_rate` as a quoted decimal string into fixed-point
  milli-units.
- Reject duplicate SKUs, empty product lists, invalid dates, negative values,
  and capacity too small for initial stock.
- Keep scenario loading separate from config loading; config chooses the path,
  the scenario loader parses the file.

Seed command behavior:

- `seed --reset` removes or recreates only the configured retail database.
- `seed` without `--reset` fails when retail state already exists.
- Seed inserts shop state, products, and initial inventory in one transaction.

## Phase 6: Rig-Backed Decision Agent Adapter

Create `src/infrastructure/agents/rig_replenishment/`.

Responsibilities:

- Implement the application `ReplenishmentDecisionAgent` port.
- Build a Rig agent using the configured chat model and OpenAI client only when
  `decide` or `run-cycle` needs decisions.
- Do not require `OPENAI_API_KEY` for `seed` or `simulate`.
- Use a concise autonomous workflow preamble, not support-chat instructions.
- Expose Rig tools as implementation details:
  - `get_inventory_snapshot`
  - `list_open_restock_orders`
  - `analyze_restock_options`
  - `place_restock_order`
  - `get_profit_summary`

Tool behavior:

- Tools should operate on a per-decision in-memory `DecisionSession`, not write
  directly to Diesel.
- `place_restock_order` appends a proposed restock order to the session and
  returns validation feedback from application/domain rules.
- At the end of the model turn, the adapter returns accepted proposals and
  summary text to `RunRestockDecision`.
- `RunRestockDecision` performs the durable write in a validated application
  transaction.
- Tool output must redact provider prompts and avoid logging sensitive model
  payloads.

Prompt shape:

- Ask the model to inspect snapshot, ranked options, open inbound orders, and
  profit summary.
- Require the model to place no more than `max_restock_orders_per_decision`.
- Require each proposal to include SKU, quantity, and short rationale.
- Tell the model to prefer candidates with high expected gross profit per space
  unit while avoiding capacity overflow and duplicate inbound orders.

Adapter tests:

- Unit test tool argument parsing and session proposal recording.
- Test adapter failure mapping without calling the real provider.
- Do not require OpenAI network access in normal tests.

Manual acceptance criteria:

- `seed` creates a retail SQLite database from `data/retail_scenario.yaml`.
- `simulate` advances the logical shop date, receives due restocks, records
  sales and lost sales, and updates inventory deterministically.
- `decide` creates a decision run, gathers a snapshot, obtains proposals from
  the decision-agent port, validates them, and persists accepted restock orders.
- `run-cycle` runs the autonomous workflow without chat input.
- Domain code has no Diesel, Rig, Clap, environment, async runtime, or provider
  payload dependencies.
- Diesel schema and row types stay private to infrastructure.
- Tests use in-memory fakes for application ports and real migrations for
  Diesel adapter coverage.
- No unsafe code remains in crate-owned source.
